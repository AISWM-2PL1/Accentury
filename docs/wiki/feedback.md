# 이용 후기 (KAN-211)

결과 화면에서 응시자가 개발팀에 보내는 서술 후기. 2026-09-15 구현 완료(1~4단계).

- 계약·저장: `backend/src/main/java/app/accentury/backend/feedback/`, `V12__session_feedback.sql`
- 화면: `web/src/feedback/`, `web/src/result/ResultScreen.tsx`
- 방침 반영과 그 근거: [`privacy-policy.md`](privacy-policy.md) (1·4·5·6·11·12항)
- 계측 규칙: [`analytics.md`](analytics.md) · 슬랙 값 주입: `infra/README.md` 「이용 후기 슬랙 알림」
- E2E: [`browser-e2e.md`](browser-e2e.md), `web/e2e/feedback.spec.ts`

## 1. 왜 GA4가 아니라 자체 API인가

「후기를 받는다」는 요구에 계측 이벤트를 하나 더 쓰는 길이 먼저 떠오르지만, 그 길은 둘에서 막힌다.

- **길이.** GA4 이벤트 파라미터의 문자열 값은 100자가 상한이다. 후기 본문은 500자를 받기로 했고,
  자르면 정작 하고 싶은 말이 잘린다.
- **PII.** 회신용 이메일은 개인 식별 정보다. 계측 스트림에는 사용자 ID도 광고 식별자도 싣지
  않는다는 규칙이 이 레포에 서 있고(`analytics.md` §3), 이메일 하나 때문에 그 규칙을 흔들 수 없다.

그래서 후기는 우리 서버가 받아 우리 DB에 넣는다. 계측에는 **행동 두 건만** 나간다 (§7).

## 2. 흐름

```
결과 화면 [개발팀에 후기 보내기]
   │  (부모가 멱등 키를 한 번 만든다 — ResultScreen.feedbackKey)
   ▼
FeedbackSheet (모달)  ─ 별점/본문/이메일 ─▶ sendFeedback()
                                              │ POST /v0/sessions/{id}/feedback
                                              ▼
                                        FeedbackController
                                              ▼
                                        FeedbackService
                                   인증 → 요청제한 → 멱등키 → 본문검증
                                   → [세션 행 잠금] 완료가드 → 멱등판별
                                   → 결과 스냅샷 복사 → INSERT
                                              │
                                   publish(FeedbackSubmitted) ← 트랜잭션 콜백 **안**
                                              ▼  AFTER_COMMIT + @Async
                                        FeedbackSlackNotifier
                                              ▼
                                        Slack #feedback
```

응답은 슬랙을 기다리지 않는다. 슬랙이 죽어도, URL이 없어도 저장은 201이다.

## 3. API 계약

`POST /v0/sessions/{sessionId}/feedback` (1단계 확정, `FeedbackController` javadoc이 정본)

| | 값 |
|---|---|
| 헤더 | `Authorization: Bearer <세션 토큰>` (필수) · `Idempotency-Key` (필수) · `Content-Type: application/json` |
| 본문 | `{"rating": 1~5, "body": "…", "contactEmail": "…"}` — `body`만 필수(trim 후 1~500자), 나머지는 선택 |
| 201 | 저장됨 |
| 200 | **같은 키**의 재전송 — 저장 없이 같은 응답 |
| 응답 본문 | `{"accepted": true}` (201·200 공통) |

오류는 공통 봉투(§2.3)로 돌려준다.

| 상태 | code | 언제 |
|---|---|---|
| 400 | `VALIDATION_FAILED` | `Idempotency-Key` 누락, 본문 누락·500자 초과, 별점 범위 밖, **소수 별점**(`2.5`), 이메일 형식 불량 |
| 401 | `SESSION_EXPIRED` | 토큰 누락이나 만료 |
| 403 | `SESSION_FORBIDDEN` | 다른 세션의 토큰 |
| 409 | `RESULT_NOT_READY` | 완료되지 않은 세션 |
| 409 | `FEEDBACK_ALREADY_SUBMITTED` | **새 키**로 다시 제출 (세션당 1건) |
| 429 | `RATE_LIMITED` | 세션당 분당 10건 초과 (`feedback.rate-limit-per-minute`) |

인증이 `authenticateBearerForResult`인 것이 요점이다. 완주한 세션은 `expiresAt`이 지난 뒤에도
결과를 24시간 볼 수 있는데(§5.5), 일반 `authenticateBearer`를 쓰면 **결과는 보이는데 후기만 401**이
되는 모순이 생긴다.

같은 키의 재전송에서 **본문을 대조하지 않는다.** 어휘 답안(§3.5)과 갈리는 자리다 — 후기에는
「같은 키로 다른 답」이라는 오용이 없고(고칠 답이 없다), 화면이 재전송 때 본문을 한 글자라도 다시
만들면 400이 나는 편이 사용자에게 훨씬 나쁘다.

## 4. 저장 모델

`session_feedback` (V12). 컬럼은 입력 셋과 스냅샷 다섯, 그리고 키·시각이다.

**`test_session`에 FK를 걸지 않는다.** 세션과 결과는 24시간 뒤 정리 잡이 지우는데 후기는 1년
남아야 하기 때문이다 — FK가 있으면 세션이 사라지는 순간 후기도 함께 지워지거나(CASCADE) 세션
정리가 막힌다(RESTRICT). 대신 **저장 시점에 결과 값을 복사한다**: `tier_code`, `test_version`,
`score_version`, `platform`, `traffic`. 세션 행이 사라진 뒤에도 "어떤 등급을 본 사람이 무슨 말을
했나"를 알 수 있어야 후기가 쓸모가 있다.

`traffic`을 함께 복사하는 것은 합성 트래픽(E2E 스모크, KAN-138)이 남긴 후기를 나중에 걸러내기
위해서다 — 이 스펙이 도는 판마다 후기가 한 건씩 쌓인다.

| | 값 | 근거 |
|---|---|---|
| 보존 | 1년 | `accentury.feedback.retention: 365d`, `FeedbackRetention`이 60분 주기로 `created_at` 기준 삭제 |
| 유일성 | 세션당 1건 | `ux_session_feedback_session` |
| 재응시 | 이전 후기는 **남는다** | 세션이 바뀌어도 후기 행은 세션 정리와 독립이다 |

무한 보존이 아닌 것은 선택 입력인 회신 이메일이 개인 식별 정보이기 때문이다. 언젠가는 지워져야 한다.

## 5. 슬랙 알림 (2단계)

개발팀이 후기를 읽는 곳은 채널 `#feedback` 하나다. 무료 플랜이라 수단은 Incoming Webhook 하나이고,
staging과 prod가 채널을 나누지 않는다 — 구분은 메시지 머리의 **환경 라벨**이 한다.

- **빈은 설정과 무관하게 항상 등록된다.** `admin.token`이나 `kakao-admin-key`처럼 경로를 없애는
  조건부 등록이 아니다. 슬랙은 저장의 부수 기능이라 「꺼짐」의 정의가 두 곳으로 갈리면 안 된다.
- **자리표시 값이면 꺼진다.** 값이 없거나 Terraform 자리 표시 값이면 기동 로그에
  `후기 슬랙 알림 꺼짐`이 뜨고 그대로 돈다. 로컬·테스트가 이 상태이고, **정상이다.**
- **라벨은 `accentury.result.web-test-url`의 호스트다.** staging·prod가 같은 `deploy` 프로파일을
  쓰므로(KAN-140) 프로파일로는 구분이 안 되고, 결과 URL은 이미 환경마다 다른 값이 SSM으로 들어온다.
  못 읽으면 `local`.
- **메시지 형식**: `[라벨] 새 이용 후기 ★4 · 등급 X · 정의/점수버전 · 플랫폼 · traffic · 세션 앞 8자
  · 연락처 있음|없음` + 본문을 줄마다 `>` 인용. **이메일 값은 싣지 않는다** — 채널은 개발팀 전원이
  보고 무료 플랜은 지난 메시지를 지우지 않아, 한 번 흘리면 되돌릴 방법이 없다. 답장할 후기를 만나면
  DB에서 세션 id로 찾는다(그래서 앞 8자를 싣는다).
- **본문은 이스케이프한다.** 자유 서술이라 `<!channel>`이 그대로 들어올 수 있고, 안 막으면 후기
  한 건이 채널 전체 멘션이 된다.
- **실패는 WARN 한 줄이다.** 커밋 뒤라 되돌릴 것이 없고 원본은 DB에 있다. 예외 메시지에 웹훅 URL이
  섞여 나올 수 있어 클래스 이름과 메시지만 찍고, 마지막 관문이 `LogMasking`의 `SLACK_WEBHOOK`이다.
- **큐가 넘치면 버리되 흔적을 남긴다.** 전용 실행기(워커 1~2, 큐 200)가 포화되면 알림을 버린다 —
  거절 예외를 받을 곳이 없고(커밋 뒤의 비동기 경로다) 무한 큐는 슬랙 장애를 메모리 문제로 옮긴다.
  `DiscardPolicy`를 쓰지 않는 것은 그것이 로그도 지표도 남기지 않아서다(Codex 리뷰 P1) — 폐기마다
  WARN 한 줄과 카운터 `accentury.feedback.notify.dropped`가 남는다. 이 값이 0보다 크면 실행기 용량이나
  슬랙 응답 시간을 본다. 버려진 알림의 후기는 DB에 그대로 있다.

URL 주입 절차(SSM SecureString `ACCENTURY_FEEDBACK_SLACKWEBHOOKURL`, apply 뒤 `put-parameter`)는
`infra/README.md`의 「이용 후기 슬랙 알림」 절이 정본이다. WAF 경로 규칙도 2단계에서 들어왔다
(`infra/modules/waf/main.tf`의 `feedback_path_regex`).

## 6. 웹 시트 (3단계)

`FeedbackSheet`는 결과 화면 위를 덮는 모달이다. **바깥 설문 링크로 보내지 않는다** — 앱 WebView는
새 창을 열지 못해(`setSupportMultipleWindows` off) 앱에서는 아무 일도 일어나지 않고, 브라우저에서도
응시자가 우리 화면을 떠난다.

### 상태기계

| 상태 | 화면 | 나가는 길 |
|---|---|---|
| `editing` | 입력 셋 + [보내기] | 제출 · 닫기 |
| `sending` | [보내는 중…], 입력 잠금 | 없음 — 닫기도 막는다 |
| `sent` | 완료 제목·문구 | 닫기 |
| `already` | 「이미 후기를 보냈어요」 | 닫기 |
| `expired` | 「세션이 만료돼…」 | 닫기 |
| `failed` | 실패 문구 + [다시 보내기] | 재시도 · 닫기 |

`sent`·`already`·`expired`는 **되돌아갈 수 없는 끝**이라 입력칸을 치운다. `failed`만 입력을 그대로
둔다 — 방금 쓴 글이 실패 한 번에 사라지면 사람은 두 번 쓰지 않는다.

보내는 중에는 [닫기]·Escape·배경 탭을 전부 무시한다. 요청이 서버에 닿았는지 모르는 채로 화면이
사라지면 후기가 갔는지 알 수 없다. 그 외에는 셋 다 듣는다 — 광고 동의 시트와 반대인데, 후기는
**안 쓰고 나가는 것이 정상 행동**이고 다시 조르지도 않기 때문이다.

### 멱등 키를 부모가 소유하는 이유

시트는 `submit(input)`을 받기만 하고 키를 모른다. 키는 `ResultScreen`이 시트를 열 때 한 번 만들어
재시도에 재사용한다. 시트 안에서 만들면 [다시 보내기]가 **새 키로** 나가고, 첫 요청이 실제로는
저장됐던 경우(응답만 유실) 409를 받아 「이미 보냈어요」가 된다 — 방금 쓴 글이 어디로 갔는지 알 수
없어지는 자리가 그것이다. `web/e2e/feedback.spec.ts`가 두 요청의 헤더를 대조해 이 규칙을 붙든다.

### 409는 완료다

`FEEDBACK_ALREADY_SUBMITTED`는 예외가 아니라 정상 완료로 접는다 — 새로고침 뒤 다시 보낸 경우가 그
자리이고, 사용자가 하려던 일(후기가 개발팀에 닿는 것)은 이미 이루어져 있다. 분기는 HTTP 상태가
아니라 봉투의 `code`로 한다: 같은 409라도 `RESULT_NOT_READY`는 뜻이 정반대다.

### 진입 버튼은 글자 버튼이다

결과 화면 푸터에는 이미 주버튼 하나와 보조 둘이 서 있다. 후기는 세 번째 출구가 아니라 부가
행동이라 보조의 무게(테두리)를 주면 주 출구인 공유·재응시와 같은 급으로 읽힌다 (ux-ui.md Hick's
law). 보낸 뒤에는 버튼을 한 줄 인사로 바꾼다 — 결과당 1건이라 두 번 열 이유가 없고, 버튼을 남기면
눌러 본 사람이 「이미 보냈어요」를 받는데 그건 실패로 읽힌다.

### 스타일을 `.ad-consent-*`에서 복사한 이유

막·패널·여백·반경·안전영역·버튼 스택의 값이 광고 동의 시트의 사본이다. 공용 클래스로 뽑거나 저쪽
이름을 빌려 쓰지 않았다 — `.ad-consent-*`는 iOS 스모크 구동기가 화면을 가르는 선택자라
(`nativeSmokeSelectors.test.ts`), 개명하는 순간 스모크가 멈추고 광고 시트의 회귀 위험을 이 티켓이
떠안는다. **세 번째 시트가 생기는 날** 공통 부분을 뽑는다 — 둘일 때 미리 뽑으면 「무엇이 공통인가」를
사례 둘로 정하게 되고, 지금도 패널 높이와 입력 필드가 갈린다.

### 포커스 트랩과 스크롤 잠금은 없다

`role="dialog"` + `aria-modal="true"`로 뒤를 떼어 놓고, 제목을 `aria-labelledby`로 잇고, 열리는 순간
초점을 본문 입력칸에 둔다. 거기까지다 — 레포의 다른 모달(`AdConsentSheet`)에 없는 장치라 한쪽에만
세우면 같은 모양의 두 화면이 키보드에서 다르게 움직인다. 세운다면 **둘 다 같이** 세우는 별도 작업이다.

## 7. 계측

| 이벤트 | 파라미터 | 언제 |
|---|---|---|
| `feedback_opened` | 없음 | 시트를 열었다 |
| `feedback_submitted` | `rating` (없으면 null) | 저장됐다 (`saved`) |

둘의 차이가 「열어 보고 안 쓴 비율」이다.

**올리는 값은 별점 하나뿐이다.** 본문과 이메일은 개인을 특정할 수 있는 값이라 계측에 실리는 길
자체를 만들지 않았다 — `ResultScreen`의 `onFeedbackSubmitted`가 `rating`만 받는다. `already`에는
계측을 보내지 않는다: 그 응답은 **이번에 저장된 것이 없다**는 뜻이라, 세면 한 사람의 후기 하나가
둘로 쌓인다.

## 8. 방침에 반영한 것

`infra/privacy/privacy.html` 여섯 자리다. 판단 근거는 [`privacy-policy.md`](privacy-policy.md) §1이
정본이고 여기는 목록만 든다.

| 절 | 무엇 |
|---|---|
| 1항 표 + 아래 산문 | 「이용 후기」 행(항목·목적·1년)과 절 — 이메일은 선택·회신 전용, 내부 알림 비적재 |
| 4항 | Slack Technologies, LLC (미국) 국외 이전 — 이메일은 가지 않는다 |
| 5항 | 1년 뒤 자동 삭제, 재응시해도 남음 |
| 6항 | 이메일을 적은 경우의 열람·삭제 요청 경로 (13항 문의처) |
| 11항 | 이메일은 로그와 내부 알림에 남기지 않음 |
| 12항 | 선택 입력 + 시트 안내 + 방침 링크 → [보내기]를 동의로 본다 |

**6항이 이 티켓의 무게중심이다.** 방침의 전제는 「개인을 알아볼 수 있는 값이 없다」였는데 회신
이메일이 그 전제를 부분적으로 깬다 — 계정 없는 서비스에서 이용자를 지목할 수 있는 유일한 경로라,
삭제·열람을 요청할 길을 적지 않으면 권리 행사 자체가 불가능해진다.

- **마이그레이션 번호.** V10·V11을 KAN-210이 가져가 후기 테이블은 **V12**였다 (KAN-220 재베이스라인으로
  2026-09-21 이후 V1 하나에 합쳐졌고, 다음 번호는 V2부터다). 브랜치를 나눠 작업하면
  같은 번호를 두 티켓이 쓰는 일이 생긴다 — 분기 전에도, Dev를 리베이스로 받아올 때도
  `ls db/migration`으로 확인한다.
- **`Map.of`는 10쌍이 상한이다.** 11번째 인자부터 컴파일이 안 된다. 스냅샷 필드가 늘면
  `Map.ofEntries`로 바꾼다.
- **`@TransactionalEventListener`는 트랜잭션 **안**에서 발행해야 한다.** `AFTER_COMMIT` 리스너는
  활성 트랜잭션 안에서 발행된 이벤트만 받고, 밖에서 발행하면 기본값(`fallbackExecution = false`)에서
  **조용히 버려진다** — 예외도 로그도 없다. `FeedbackService`가 트랜잭션 콜백 안에서 발행하는 이유다.
- **`smallint` ↔ `Short`.** 별점 컬럼이 `smallint`라 엔티티 타입도 `Short`다. `Integer`로 두면
  매핑에서 걸린다. 변환은 서비스가 한다.
- **요청 본문의 별점은 `Number`다 — `Integer`가 아니다.** `Integer`로 받았을 때 `{"rating": 2.5}`가
  400이 아니라 **2로 잘려 201로 저장됐다**(2026-09-15 실측, Codex 리뷰 P1). 화면이 `Number.isInteger`로
  거르고 있어 드러나지 않았을 뿐 BE 계약에는 구멍이었다. 원본 수를 그대로 받아 `FeedbackService`가
  정수인지 판정한다 — 값만 보므로 `5.0`은 통과한다. 전역 ObjectMapper 설정은 건드리지 않았다(다른
  엔드포인트의 역직렬화까지 함께 바뀐다).
- **`@EnableAsync`가 레포에 처음 들어왔다.** 앞으로 **실행기 이름 없는 `@Async`는 만들지 않는다** —
  이름이 없으면 컨텍스트 기본 실행기로 떨어지는데, 이 앱에는 AI 전달 풀(`analysisExecutor`)처럼
  용량이 좁은 실행기가 있어 알림 하나가 분석 전달을 밀어낼 수 있다.
- **terraform이 로컬에 없어 `validate`를 못 돌렸다.** WAF 경로 규칙(2단계)은 정규식 리터럴과 기존
  규칙의 모양 대조로만 확인했다. apply는 배포 시 사람 손이다.
- **로컬 Node 26 vs CI Node 22.** 방침 테스트는 표준 API만 쓰지만, 웹 단위 테스트는 로컬 Node 26에서
  jsdom `localStorage`가 없어 로컬만 깨지는 일이 있다 — 그때는 `npx -y node@22`로 재현한다.

## 10. 이월·후속

- **관리자 조회 API가 없다.** 지금 후기를 읽는 길은 슬랙 채널과 DB 직접 조회 둘뿐이다. 무료 플랜
  90일이 지나면 채널에서는 사라지고 DB에만 남는다.
- **배포 시 사람 손**: 슬랙 앱 생성 → Incoming Webhook 발급 → SSM `put-parameter` → WAF apply.
  그 전까지 알림이 꺼져 있는 것은 고장이 아니다.
- **시트 둘의 공용화와 포커스 트랩** — §6의 두 자리. 세 번째 시트가 생기는 날 함께 한다.
- **재응시 후 두 번째 후기.** 지금은 세션이 바뀌면 새 후기를 쓸 수 있다(후기는 세션당 1건이다).
  같은 사람이 여러 건을 남기는 것을 막을 수단이 없고, 막을 필요가 있는지도 아직 정하지 않았다.
