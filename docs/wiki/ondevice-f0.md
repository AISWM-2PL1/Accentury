# 온디바이스 F0 추출 방식 선정 (KAN-103)

조사와 결정 기록 (2026-08-13). 실시간 피치 곡선용 온디바이스 F0 추출기를 확정한다.
전제(아키텍처 설계 원칙): 온디바이스는 **저지연 우선, 정확도는 거칠어도 됨**. 정밀 채점은 서버 RMVPE 몫.

## 결정 요약

|---|---|---|
| **Android** | **자체 Kotlin YIN 구현** (시간영역, 의존성 0) | MIT 구현(sevagh/pitch-detection, dywapitchtrack) JNI 포팅 |

## 선정 근거 상세

1. **라이선스가 결정적 제약**. TarsosDSP와 aubio는 GPLv3, Essentia는 AGPLv3. GPL 계열은 APK/IPA 배포 순간 카피레프트가 걸려 앱 전체 소스공개 의무 발생 → 상용 클로즈드소스 앱에서 즉시 탈락. 이 한 축이 "기성 라이브러리 붙이기" 경로를 대부분 제거한다.
2. **YIN은 자체 구현 비용이 낮다**. 코어(차분함수 → CMNDF → 절대 임계값 → 포물선 보간)가 100~200줄. 16kHz, 2048샘플 창에서 80~400Hz 검출은 표준 설정이고(당시 값, 2026-09-17에 60~800Hz로 변경 — 아래 「탐색 대역 60~800Hz」 절), O(W²) 시간영역 구현도 프레임당 수 ms → NFR "곡선 갱신 100ms 이하" 예산에 크게 여유.
3. **무성음 판별이 알고리즘에 내장**. 구 autocorrelation 프로토타입의 최대 문제(곡선 튐)를 YIN의 절대 임계값이 정확히 해결한다.
4. **플랫폼 일관성**. Android가 자체 YIN이면 iOS도 같은 알고리즘을 이식하는 편이 피치 곡선 특성(무성음 구간, 튐 패턴)이 양 플랫폼에서 동일해진다. AudioKit PitchTap은 알고리즘이 ptrack(Csound 이식)이라 곡선 특성이 달라짐 → 폴백으로만.
5. **의존성 0 + 테스트 용이**. 순수 Kotlin이라 합성 사인파로 JVM 단위 테스트 가능, 추후 Kotlin Multiplatform으로 iOS와 로직 공유 옵션도 열림(캡처는 플랫폼별, DSP 수학만 공유).
6. **YIN 특허**: 명시적 특허 기록을 찾지 못함. MIT 재구현(sevagh), GPL 재구현(aubio)들이 특허 경고 없이 배포 중인 것이 정황 증거. 100% 확정 문서는 없음을 기록해 둔다.

⚠️ **구현 시 주의**: TarsosDSP(GPL) 소스를 보고 옮기면 파생저작물 위험. 참고는 **논문 원전**(de Cheveigné & Kawahara, JASA 2002)과 **MIT 구현**(sevagh/pitch-detection, Beethoven YIN)만 사용한다.

## 임계값 완화와 에너지 게이트 (KAN-105)

원 논문 권장 CMNDF 임계값 0.1~0.2를 그대로 쓰니(0.15) 실제 대화 샘플에서 곡선이 조각났다. 우리 용도는 정밀 F0 측정이 아니라 실시간 억양 곡선이라 판단 기준이 "끊김 < 약간의 오검출"이다. 곡선이 끊기면 사용자가 억양을 읽을 수 없지만 한두 점이 튀는 건 곡선 모양을 해치지 않는다.

| CMNDF 임계값 | 20대 샘플 유성 판정률 | 50대 샘플 유성 판정률 | 옥타브 오류(중앙값 대비 1.8배 밖) |
| --- | --- | --- | --- |
| 0.15 | 85% | 36~48% | - |
| **0.25 (채택)** | 91% | 72~77% | 0~1개 |
| 0.30 | +2~7%p | +2~7%p | - |

0.30은 0.25 대비 이득이 작아 0.25로 정했다.

곡선 쪽 상수(EMA 계수·표시 폭·무성 유지 시간)와 체감 지연 분해는 [pitch-curve.md](pitch-curve.md)에 따로 모아 두었다.

임계값을 느슨하게 잡으면 마이크 잡음이나 무음 구간에서 CMNDF가 우연히 0.25 아래로 내려가 가짜 피치가 나올 수 있다. 그래서 `VOICED_MIN_RMS = 100f` 에너지 게이트를 함께 넣었다 - 청크 RMS가 이보다 작으면 판정 자체를 하지 않는다. 값은 `AudioQuality.QUIET_RMS_THRESHOLD`와 같아서, 점검 화면의 볼륨 판정(`VoiceCheckController`)과 곡선이 같은 문턱을 공유한다. "점검을 통과한 볼륨이면 곡선이 나온다"가 성립한다. 게이트를 CMNDF 계산 앞에 둬서 무음 프레임은 O(W·τ) 연산을 통째로 건너뛰는 부수 이득도 있다.

## 탐색 대역 60~800Hz (KAN-218, 2026-09-17)

`MIN_F0_HZ`/`MAX_F0_HZ`를 80/400에서 **60/800**으로 넓혔다. 세 플랫폼(`audio/YinPitchEstimator.kt`, iOS Core `Audio/YinPitchEstimator.swift`, 웹 `audio/yin.ts`)이 같은 값이다 — 같은 목소리가 기기마다 다른 곡선이 되면 재현되지 않는 버그로 보인다.

### 80~400이 곡선을 끊은 두 증상

사용자 레인은 화자 중심 ±7 semitone 창을 쓰고, 창 밖 음높이는 `userCurveDisplayPoints`가 y=0·y=1로 눌러 천장·바닥에 붙인다([pitch-curve.md](pitch-curve.md) §2 `USER_CURVE_SPAN_SEMITONE`). 그 clamp는 **추정기가 값을 줬을 때만** 일한다. 추정기가 대역 밖을 먼저 무성(null)으로 돌려보내면 눌러 담을 값 자체가 없다 — 대역의 양 끝이 곧 곡선이 사라지는 자리였다.

| 증상 | 구간 | 원인 |
|---|---|---|
| 선이 **끊긴다** | 80Hz 아래 | 대역 밖 → null → 무성 취급. 중심 120Hz 화자의 창 바닥이 120×2^(−7/12) ≈ 80Hz라 창 바닥과 대역 하한이 같은 자리다. 낮게 깔면 바닥에 붙는 대신 선이 사라졌다 |
| 선이 **아래로 꺾인다** | 400Hz 위 | τmin=40(400Hz)이라 450Hz의 1주기 골(τ≈35.6)은 탐색 밖. 2주기 골(τ≈71)이 첫 골이 되어 **225Hz로 읽힌다** — 한 옥타브 아래 뒤집힘. 감탄으로 올라가야 할 선이 내려갔다 |

### 왜 60~800인가

창이 대역 안에 들어와야 창 밖 값이 전부 clamp로 간다. ±7 semitone은 2^(±7/12) = ×0.6674~×1.4983이라, 60~800Hz면 **중심 90~534Hz 화자는 창 전체가 대역 안**이다(60/0.6674 ≈ 90, 800/1.4983 ≈ 534) — 낮은 남성음(vocal fry 하한 60Hz대)부터 여성 감탄·고성(800Hz)까지 들어온다. 성인 발화 중심은 대개 85~255Hz라 중심 90~534Hz 밖 화자는 사실상 없다. 창 밖 값을 어디에 그릴지는 추정기가 아니라 표시 쪽이 정한다는 역할 분담이 이것으로 성립한다.

### 옥타브 위 오류 위험과 실측

상한을 올리면 τmin이 40→20이 되어 **반주기 골**(옥타브 위 오류)을 먼저 만날 위험이 생긴다. CMNDF의 누적 정규화가 작은 τ의 골을 임계값 위로 띄워 주는 것이 YIN의 설계 의도인데, 2·3배음이 기음보다 큰 정도까지는 그 말이 맞고 2배음이 훨씬 강하면 뚫린다(아래 「2τ 골 검사」).

| 450·520·600Hz 배음 신호, 62·70Hz 유성, 790/820Hz 경계 | 통과 | 웹 `yin.test.ts`·Android `YinPitchEstimatorTest.kt`·iOS Core `YinPitchEstimatorTests.swift` — 「옛 상한(400Hz) 위의 고음은…」「옛 하한(80Hz) 아래의 저음도…」「대역 상한 경계 790Hz…」「대역 밖 820Hz…」 |

### 2τ 골 검사 (Codex 리뷰 반영)

**재현.** 기음 250Hz 진폭 3000, 2배음 8000(2048샘플 16kHz)을 넣으면 대역만 넓힌 코드는 503Hz를 냈고 origin/Dev(80~400Hz)는 250Hz였다. τ 탐색이 짧은 τ부터 임계값(0.25) 아래 첫 골에서 멈추는데, 2배음이 우세하면 반주기 골의 CMNDF가 0.25 아래로 내려온다. 옛 대역은 τmin=40이라 기음 200Hz 이상의 반주기(τ<40)가 탐색 밖이어서 우연히 보호됐고, 기음 190Hz 이하(남성 음역)는 옛 코드도 같은 오류가 있었다(2·4배음 우세 프로파일 80~190Hz 전부 옥타브 위). 새 대역은 200~400Hz(여성 음역)를 새로 노출시켰고, 고치면 남성 음역까지 같이 좋아진다.

**규칙** (세 플랫폼 3.5단계, 상수 `OCTAVE_CHECK_MARGIN = 0.1`). 첫 골 τ(국소 최솟값까지 하강한 뒤)를 잡은 다음:

```
t2 = 2τ
if t2 + 2 <= tauMax:
    best = argmin cmndf[k], k ∈ [t2−2, t2+2]
    best를 국소 최솟값까지 하강 (위로는 tauMax, 아래로는 τ 초과까지)
    if cmndf[best] < cmndf[τ] − 0.1: τ = best
```

그다음 기존 4단계(포물선 보간·clamp). 근거: 진짜 주기 T의 골은 CMNDF≈0이지만 2배음 우세로 생긴 반주기 골은 홀수 배음이 어긋나 0.1~0.25 사이에 머문다 → 2τ 쪽이 0.1 이상 더 깊으면 반주기 골로 본다. 진짜 고음(400~800Hz)은 2τ 골도 ≈0이라 차이가 0.1을 못 넘어 뒤집히지 않는다.

**마진 실측** (2026-09-17, 웹 프로토타입, 레포에 안 남김). 5개 프로파일(순음 / 기음 우세 / 2배음 2배 우세 / 2배음 4배 우세 / 2·4배음 우세) × 70~780Hz 10Hz 간격 × 프레임 내 5% pitch drift 유무:

| 마진 | 결과 |
|---|---|
| 0.05 | 2·4배음 우세 780Hz에서 옥타브 아래 3건 |
| 0.10 | 0건 — 채택 |
| 0.15 | 2배음 4배 우세 프로파일 전부 놓침 |

**실음성** (`app/src/debug/assets/fake_mic.wav`, 50대 여성 2.5초, 창 2048 hop 512 = 75프레임): 57 유성 프레임 중 1프레임(199→99, 이웃이 98·197로 원래 애매한 프레임)만 바뀌고 나머지 동일.

**회귀 방지력.** 검사 코드를 빼면 「2배음이 기음보다 강해도…」(120→242, 250→503, 350→704Hz)와 「2·4배음 우세 프로파일…」(100→200, 200→401, 300→602Hz)이 세 플랫폼 모두 실패한다(2026-09-17 확인). 기음 우세 「진짜 고음은…」은 검사 유무와 무관하게 통과한다 — 검사가 진짜 고음을 건드리지 않는다는 뜻이다.

### 연산량·프레임 시간

| | 80~400 | 60~800 |
|---|---|---|
| τ 범위 (16kHz) | 40..200 | 20..266 |
| 적분 창 W (2048 창 − τmax) | 1848 | 1782 |
| O(W·τmax) 곱셈/프레임 | ≈37만 | ≈47만 (+28%) |
| iOS 디버그 빌드 프레임 시간 | 26ms | 35ms |
| iOS 릴리스 빌드 | 0.23ms (실측) | 미측정 — 비례하면 0.3ms 안팎 |

적분 창이 τmax(266)보다 커야 한다는 조건(`window <= tauMax → null`)은 2048 창에서 여유가 크다. 갱신 주기 32ms·NFR 100ms 예산과 견주면 릴리스 빌드에서는 여전히 미미하다.
