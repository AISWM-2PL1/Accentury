# 실시간 피치 곡선 파라미터 (KAN-105)

사용자의 '내 억양' 곡선을 만드는 상수들의 값과 그 값을 고른 근거. 기록 시점 2026-08-25, 브랜치 `feature/KAN-105-pitch-curve-polish`.
F0 추출기 자체의 선정 근거는 [ondevice-f0.md](ondevice-f0.md), 곡선이 화면에서 맡는 역할은 [ux-ui.md](ux-ui.md) §4-D가 정본이다. 이 문서는 그 사이, **"숫자를 왜 이 값으로 뒀는가"**만 다룬다.

여기 적힌 값 중 실기기에서 눈으로 확인한 것은 아직 없다. 전부 실측 데이터(샘플 음원 분석)와 계산으로 정한 잠정값이고, 확인 여부를 표에 그대로 적어 둔다. 마지막 절의 체크리스트가 실기기 단계에서 채울 칸이다.

## 1. 파이프라인 한 줄

```
마이크 512샘플 read (AudioRecorder)
  → OverlappedFramer (2048창 / 512hop)
  → YinPitchEstimator (CMNDF 0.25, RMS 게이트 100)
  → RecordingEngine.PitchFrame (창 중앙 시각 + F0 또는 null)
  → UserCurve (중심 창 · EMA · 무성 처리)
  → CurveLane (중간점 2차 베지어)
```

각 단계는 앞 단계가 뭘 하는지 모른다. 프레임 시각이 창 중앙이라는 사실도 `RecordingEngine`에서 한 번 정해지고 아래로는 그냥 "시각"으로 흐른다 — 그래서 시간축을 옮기는 결정이 한 줄로 끝난다.

**시각은 창의 시작이 아니라 중앙이다.** YIN이 낸 F0 하나는 창 전체(2048샘플 = 128ms)를 대표하는 값이라, 시간축 위의 대표 위치도 그 한가운데가 맞다. 시작 시각으로 찍으면 곡선이 실제보다 64ms 앞당겨 그려져 같은 시간축에 놓인 가이드 곡선과 정렬이 어긋난다. 체감 지연은 이 규칙과 무관하다 — 값이 나오는 시점이 창을 다 채운 뒤라는 사실은 그대로고, 달라지는 건 시간축 위의 **위치**뿐이다.

## 3. 체감 지연 분해

"소리를 냈다"와 "곡선이 그 소리를 그렸다" 사이에 무엇이 얼마씩 끼는지.

| 구간 | 크기 | 성질 |
|---|---|---|
| 창 채우기 | ~128ms | 원리적. 창이 다 차야 YIN이 돌아간다 |
| EMA 스무딩 | ~107ms | 파라미터 (α=0.3의 시정수) |
| 방출 + 렌더 | ~50ms | 청크 방출 주기 32ms + Compose 한 프레임 |
| 캡처 버퍼 | 20~50ms | AudioRecord 내부 버퍼, 단말마다 다름 |
| **합계** | **≈ 300ms** | |

> 값이 나오는 시점은 창 시각과 무관하다. 창 중앙 시각(§1)은 그려지는 **위치**를 옮길 뿐, 이 표의 어느 줄도 바꾸지 않는다.

**줄일 손잡이는 둘뿐이다.**
- α를 올린다(0.4 → −27ms, 0.5 → −43ms). 대신 YIN의 프레임 단위 떨림이 그대로 보인다. 지연을 줄이는 가장 싼 방법이라 실기기 튜닝의 1순위다.
- 창을 1024로 줄인다(−64ms). 대신 2048/16kHz가 담보하던 저음 검출이 위험해진다 — τ 탐색 범위가 좁아져 80~120Hz 남성 화자에서 검출이 무너질 수 있다. α를 다 써 본 뒤에나 건드릴 손잡이다.

⚠️ **에뮬레이터에서 들리는 지연은 이 표와 무관하다.** 가짜 마이크(§6)를 끼우면 `MonitoredPcmSource`가 청크를 `AudioTrack`으로 한 번 더 써 주는데, 그 재생 버퍼(0.5초 분량)와 에뮬레이터의 호스트 오디오 경로가 더해져 "소리보다 곡선이 먼저 나오는" 것처럼 보인다. 모니터는 진단용 관찰 장치라 분석 경로에 들어가지 않고, 실기기에는 아예 씌우지 않는다(하울링). 체감 지연은 실기기에서만 판정한다.

## 4. 무성 구간과 인과성

무성 구간은 길이로 갈라 다룬다. `HOLD_MAX_GAP_MS` 이하의 짧은 구멍이면 직전 값을 그대로 한 점 두어 선을 잇고, 넘으면 아무것도 두지 않아 선이 끊긴다 — 다음 유성 프레임에서 새 선분이 시작되고 EMA도 그 값으로 초기화된다. 무조건 이으면 쉼 구간에 긴 가짜 평선이 생기고 다음 발화의 첫 값이 옛 값에 끌려가며, 무조건 끊으면 한 어절 안에서도 자음마다 선이 조각난다. 판정 기준이 프레임 개수가 아니라 `timestampMs` 차이인 것도 같은 이유다 — 청크 경계에서 프레임 수는 흔들려도 시각은 흔들리지 않는다.

### 시간 가중 EMA — "선을 잇는가"와 "옛 값을 끌고 오는가"의 분리

처음에는 두 결정이 `withinHold` 하나에 묶여 있었다. 그래서 유지 한계를 늘리는 순간 "구멍이 200ms든 40ms든 새 값은 옛 값에 70% 끌려간다"가 딸려 왔다 — 구멍이 길수록 그 옛 값은 못 믿을 값인데도 그랬다. 한계를 100ms에 묶어 둔 것도 이 부작용 때문이었지, 100ms가 자음 구간의 실제 길이라서가 아니었다.

EMA를 시간 기준으로 바꾸면 결합이 풀린다. 직전 유성 프레임과 벌어진 간격을 프레임 수로 환산해 `retain = (1-α)^gapFrames`를 옛 값에 곱한다.

| 구멍 | gapFrames | 남는 옛 값 |
|---|---|---|
| 32ms (연속) | 1 | 70% — 기존 식과 **정확히** 같다 |
| 100ms | 3 | 34% |
| 250ms | 8 | 6% |
| 500ms | 16 | 0.3% |

연속 프레임에서 결과가 바뀌지 않으므로 기존 곡선의 스무딩 감각은 그대로고, 구멍만 다르게 다뤄진다. 이제 `HOLD_MAX_GAP_MS`는 **선분을 가를지**만 정하고, 옛 값의 몫은 간격이 연속적으로 정한다. 한계를 250으로 올릴 수 있게 된 것이 이 분리의 값이다. 끊김 뒤 첫 값을 `st` 그대로 놓는 것도 같은 식이 이미 내놓는 답(6% 이하)을 정확히 0으로 못박는 일에 가깝다.

### Review 화면의 구멍 보간

`fillShortGaps`가 Review 상태에서만 프레임 목록을 한 번 거른다. 두 유성 프레임 사이의 구멍이 `REVIEW_FILL_MAX_GAP_MS` 이하면 semitone 선형 보간으로 채우고, 넘으면 진짜 쉼으로 보고 둔다. 앞뒤 가장자리의 구멍(녹음 시작 전·끝난 뒤)도 이어 줄 반대쪽 이웃이 없어 그대로 둔다.

Hz가 아니라 log 영역에서 보간하는 이유는 곡선의 y축이 semitone이기 때문이다 — Hz 선형 보간은 화면 위에서 아래로 휜 선이 된다. 200Hz와 800Hz의 한가운데는 500Hz가 아니라 기하평균 400Hz다. EMA를 semitone에 거는 것과 같은 근거다.

**녹음 중에는 하지 않는다.** 실시간 곡선이 뒤 프레임을 보면 프레임이 쌓일 때마다 이미 그린 과거가 다시 그려진다. Review는 녹음이 끝나 데이터가 완성된 뒤라 양옆을 다 보고 이어도 거짓이 아니다. 가이드 곡선이 이미 같은 규칙으로 무성 구간을 잇고 있어(`guideCurveDisplayPoints`), 이것으로 위아래 두 레인의 규칙이 맞아떨어진다. 메운 프레임을 EMA가 다시 스무딩해도 무해하다 — 보간값은 직선 위에 놓여 있어 스무딩이 거의 움직이지 않는다.

이 파이프라인의 **녹음 중** 계산은 전부 **인과적**이다. EMA는 직전까지의 값만 보고, 유지 판정은 직전 유성 시각만 보고, 베지어는 이웃 두 점의 중간점을 끝점으로 써서 이미 들어온 점만으로 구간이 확정된다. 중심 음높이도 처음 8개로 잠근 뒤 다시 계산하지 않는다. 실시간 곡선에서 미래를 한 점이라도 참조하면 프레임이 쌓일 때마다 과거가 다시 그려지고, 사용자 눈에는 곡선이 저 혼자 꿈틀대는 것으로 보인다. 스플라인·중앙값 필터처럼 양옆을 보는 매끄러움은 **녹음이 끝난 뒤의 확인 화면에서나** 쓸 수 있다.

### Review 화면의 창 길이

Review에서는 `reviewWindowMs`가 창을 "녹음 전체 길이(마지막 프레임 시각 + 32ms)"와 라이브 창 중 긴 쪽으로 잡아, 미끄러지던 창이 처음부터 끝까지 다 담게 만든다. 녹음 중에는 지금 내 목소리가 오른쪽 끝에 붙어야 하니 창이 미끄러지는 게 맞지만, 끝난 뒤에 볼 대상은 방금 한 발화 전체다 — 라이브 창을 그대로 두면 정작 다시 볼 수 있게 된 시점에 마지막 2초 말고는 못 본다. 가이드도 `alignGuideToWindow`로 같은 창에 정렬되므로 발화가 길수록 왼쪽에 작게 놓이는데, 그게 두 레인의 같은 x가 같은 시각이라는 규칙이 유지된다는 뜻이라 의도된 모양이다. 창 선택은 `RecordingScreen`의 한 자리에서만 하고 곡선과 가이드가 그 값을 같이 쓴다 — 갈리면 시간축이 어긋난다.

## 5. 목소리 점검 화면과의 관계

시작 게이트의 목소리 점검(`VoiceCheckController`)이 "안녕하세요" 한 마디에서 두 값을 확정해 넘긴다.

- **centerHz** — `userCurveCenterHz`가 잡은 중심을 `Ready` 상태에 실어 보내고, 이후 모든 문항의 `userCurveDisplayPoints(centerHz = ...)`가 그 값을 y축 중심으로 쓴다. 문항마다 다시 잡으면 같은 사람의 곡선이 문항마다 다른 축에 놓인다.
- **볼륨 문턱** — `VOICED_MIN_RMS = 100f`가 `AudioQuality.QUIET_RMS_THRESHOLD`와 같은 값이다. 덕분에 "점검을 통과한 볼륨이면 곡선이 나온다"가 성립한다. 두 값이 갈리면 점검은 통과했는데 곡선은 안 그려지는 구간이 생기고, 사용자에게는 설명할 방법이 없다.

## 6. 개발 도구 — 가짜 마이크

에뮬레이터 마이크는 무음(0)만 준다. 곡선을 다듬으려면 매번 같은 음성이 필요하므로 디버그 빌드에 한해 assets의 WAV를 마이크 자리에 끼울 수 있다.

```bash
./gradlew :app:installDebug -PfakeMic=fake_mic.wav
```

Android Studio의 Run 버튼은 gradle 프로퍼티를 넘길 수 없어서, `local.properties`(gitignore 대상)에 `fakeMic=fake_mic.wav`를 적으면 같은 효과다. 둘 다 없으면 `BuildConfig.FAKE_MIC_ASSET`이 빈 문자열이라 평소대로 마이크를 쓰고, 릴리스 빌드는 이 필드가 상수 `""`로 고정돼 파일 재생 경로 자체가 없다.

| 항목 | 현재 |
|---|---|
| asset | `app/src/debug/assets/fake_mic.wav` — 경남 50대 여성, 2.5초, 유성 판정률 77% |
| 포맷 | 16kHz 모노 16bit 고정. 리샘플·다운믹스를 하지 않는다 — 조용히 변환해 주면 실제 마이크와 다른 조건에서 곡선을 보게 된다 |
| 페이스 | 마이크와 같은 512샘플 단위, 청크가 담는 시간만큼 쉬어 가며 흘린다(`realtime = true`). 그래야 스무딩 계수와 체감 지연을 평가할 수 있다 |
| 모니터 | 파일 소스일 때만 `MonitoredPcmSource`가 씌워져 지나가는 청크를 스피커로도 낸다. 곡선이 이상할 때 파일 탓인지 분석 탓인지 귀로 가른다 |

## 7. 실기기 튜닝 체크리스트

아래 칸은 실기기 확인 단계(KAN-105 4단계)에서 채운다. 비어 있으면 아직 안 한 것이다.
